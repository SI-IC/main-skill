## Проблема (кейс ERP_NEW, github.com/SI-IC/ERP_NEW)
Проект тестируется центральной дирой apps/api/tests/unit/ с именами ПО ФИЧЕ (auth_cookies.spec.ts, step_up.spec.ts), а findPairedTestFile (hooks/lib/checks.js) ищет кандидатов только ПО ИМЕНИ файла-источника (<base>.spec.ts в same-dir / tests/unit / SHARED_LOGIC_TEST_DIRS / mirror). Итог: код фактически покрыт, D блокирует, Claude массово выписывает каталожные MAIN_SKILL_VERIFY_IGNORE_GLOBS (controllers/**, middleware/** — так и появились в ERP). Это ГЛАВНЫЙ источник широких глобов.

## Что сделать
Fallback второго шанса в D-ветке (verify-changes.js, блок D, рядом с findPairedTestFile): если прямой парный не найден — искать упоминание базового имени источника в содержимом спеков центральных тест-дир пакета (tests/**, spec/**, __tests__/**  от package-root, см. findPackageRoots).
- Матчить import/require-строки: /<basename без ext>(\.js)?['"]/ подстрокой; учесть Adonis-алиасы (#controllers/auth_controller, #middleware/...) и относительные пути.
- Читать ТОЛЬКО *.spec.*/*.test.* файлы через readRepoFileSafe (checks.js — realpath+confinement+size-cap 200KB, добавлен в v1.9.0); кап на число файлов (~200) и bounded regex — I/O-DoS и ReDoS-грабли задокументированы в CLAUDE.md (секция «Триггер M», Hardening).
- False positive (спек импортирует, но не ассертит) — осознанно приемлем: лучше, чем толкать к глобам/VERIFY_CHANGES=0.
- Результат кешировать в пределах одного прогона хука (один grep-скан на Stop, не пер-файл).

## Синхронизация (обязательно, триггер D самого репо)
checks.js + checks.test.js (unit: находит по импорту/алиасу; не находит без упоминания), verify-changes.test.js (integration: src + tests/unit/feature.spec.ts с импортом → D молчит), reasonD в verify-changes.js (сейчас советует MAIN_SKILL_VERIFY_CHANGES=0 для централизованных репо — заменить на «именуй по источнику ИЛИ fallback найдёт по импорту»), CLAUDE.md секция Skip-rules, bump version.
