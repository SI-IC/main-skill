# Премортем — разобранный пример + классы контрактов

Читай при первом `<premortem>` в сессии. Цель — активировать конкретное знание о контрактах внешних систем ДО написания кода: автор и критик конкурируют за одну траекторию, поэтому сомнение выделено в отдельный шаг, где оно — единственная задача момента.

## Задача-пример

«Бот шлёт саммари ночного прогона проверок в Telegram-чат команды». Типичный happy-path код: собрать текст из результатов, `POST /sendMessage` с `parse_mode: Markdown`, `throw` при `!res.ok` в цикле по чатам.

## Премортем (то, что должно было появиться до кода)

Строки примера начинаются с `#` намеренно: `#`-комментарии парсер хука игнорирует, поэтому дословная копипаста примера триггер N не закроет. Свои гипотезы пиши без `#`.

```
<premortem>
# telegram sendMessage: text >4096 символов после парсинга entities (длинные stack traces) → 400 MESSAGE_TOO_LONG, отчёт потерян именно в ночь с максимумом падений → чанковать/усекать до отправки + тест на длинный error
# parse_mode=Markdown: непарный `*`/`_`/`` ` `` в имени проверки или error-тексте → 400 can't parse entities → escape юзер-текста (или MarkdownV2 с полным экранированием)
# рассылка по chatIds в цикле: ~30 msg/sec глобально, ~20 msg/min в один групповой чат → 429 с parameters.retry_after, который код не читает → троттлинг + уважать retry_after
# бот заблокирован юзером / кикнут из чата → 403 Forbidden на одном chatId, throw обрывает цикл — остальные без отчёта → изоляция ошибок per-recipient (allSettled / try-continue)
# results=[] из-за упавшего раннера → «✅ все проверки зелёные» — ложный успех (плюс пустой text → 400 message text is empty) → различать «нет данных» и «нет падений»
</premortem>
```

## Классы контрактов — перебирай по каждому касанию внешней системы

- **Лимиты размера/количества**: длина сообщения/поля, payload size, batch count, глубина вложенности.
- **Форматы и кодировки**: escape под parse_mode/HTML/SQL/shell, unicode/emoji, инъекция юзер-текста в формат.
- **Rate limits и тайминг**: msg/sec, req/min, таймауты запроса и провайдера, окно ретраев.
- **Доставка и идемпотентность**: at-least-once (webhook ретраится → дубли side-effects), порядок событий, гонка «событие пришло раньше записи в БД».
- **Состояние контрагента**: заблокирован/удалён/кикнут/не активирован/нет прав, протухший токен.
- **Единицы измерения**: центы vs доллары, zero-decimal валюты (JPY), ms vs s, байты vs символы.

## Правила

- По каждому классу — точный факт: число, код ошибки, имя поля ответа, идентификатор кода или термин механизма (идемпотентность / ретрай / кодировка / гонка — хук принимает и чисто-кириллическую конкретику). Не помнишь → WebFetch официальной доки метода; «наверняка есть какой-то лимит» — не гипотеза, и нумерация строки числом не считается.
- Каждая подтверждённая гипотеза → guard в коде + тест на реальный error-shape (`{ok:false, error_code:400, description:"Bad Request: message is too long"}`), запись в `<edge-cases>`.
- Гипотеза не подтвердилась доками — выкинь, не тащи мусор в блок: 3–5 конкретных лучше 10 расплывчатых.
