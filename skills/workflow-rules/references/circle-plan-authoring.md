# Авторинг плана под circle-skill

Когда план не влезает в одну сессию — оформи его так, чтобы плагин **circle-skill** исполнял
его пофазно (по фазе на свежую фоновую сессию). Цель: формат совместим, фазы самодостаточны,
размер фаз комфортен для отдельной сессии.

Перед записью прогони полный Alignment (фаза 2 workflow-rules) по ВСЕМУ плану сразу: уточни у
пользователя требования, выбери подходы, проговори edge-cases — потому что в фоновых сессиях
спросить уже нельзя.

## Формат файла (контракт circle-skill)

План — markdown в `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`. Структура:

```
# <Заголовок плана>

## Контекст
<2–5 абзацев: что строим, для кого, текущее состояние, ключевые решения с обоснованием.>

## Стратегия
<Доменный граф зависимостей, порядок фаз, общие контракты между фазами.>

## Карта кодовой базы
<Навигационный индекс, снятый ОДИН раз при планировании (когда весь репозиторий в контексте)
и переиспользуемый всеми фазами: где живут ключевые подсистемы, entrypoints, ключевые модули,
конвенции — «куда смотреть за чем». Компактный индекс, НЕ дамп файлов: читается каждой фазой,
раздутая карта жжёт токены в каждой сессии. Greenfield-план (существующего кода нет) — вместо
карты опиши целевую структуру каталогов.>

## Риски
<Что может пойти не так в целом по плану + как фазы это смягчают.>

## Фаза 1 — <домен/название>
<!-- circle: status=pending order=10 deps=[] autonomy=auto obstacle="" -->

<тело фазы — см. ниже>

## Фаза 2 — <домен/название>
<!-- circle: status=pending order=20 deps=[1] autonomy=auto obstacle="" -->

...

## Журнал
```

Жёсткие правила парсера circle (не отступай):

- Заголовок строго `## Фаза <id> — <title>`. `<id>` без пробелов (`1`, `2`, `2a`). Разделитель `—` или `-`.
- Маркер `<!-- circle: ... -->` — в пределах 5 строк под заголовком фазы.
- `order` — int, ключ сортировки; шаг 10 (10, 20, 30 — оставляет место для вставок).
- `deps=[<id>,...]` — id предшественников; удовлетворяются ТОЛЬКО когда те `done`. Не ставь в deps
  фазу, которая `skipped`/`needs-human` — зависимая зависнет в `pending`.
- Стартовый `status` всех фаз — `pending`. `obstacle=""`.
- `## Журнал` оставь пустым (только заголовок) — фазы дописывают записи уровня `###` сами.
- Преамбулу `## Контекст` / `## Стратегия` / `## Карта кодовой базы` / `## Риски` executor читает
  на старте КАЖДОЙ фазы — это общий контекст. Не дублируй её в тело фаз.

## Тело каждой фазы — самодостаточность

Фоновая сессия не задаёт вопросов. Поэтому в теле фазы:

- **Выбранный подход + отвергнутая альтернатива + обоснование** — решение уже принято, не
  переоткрывай его в сессии.
- **Файловый манифест** — точный список путей, которые фаза создаёт/меняет, снятый при
  планировании (когда репозиторий в контексте), чтобы фоновая сессия не переоткрывала географию
  кода вслепую. На каждый путь — одна строка: `создать|изменить` + что именно (**имя символа/
  функции/секции, НЕ номер строки** — строки плывут от фазы к фазе) + зачем. Executor трактует
  манифест как **сильный приор, не догму**: сверяет, что файл ещё соответствует описанной роли;
  разошлось (файл переехал/переименован/отрефакторен ранней фазой) — падает в целевой поиск и
  пишет расхождение в журнал. Greenfield-фаза — перечисли создаваемые файлы.
- **Шаги имплементации** — конкретные, по файлам/модулям (опираются на манифест выше).
- **Edge-cases** для этого домена (из чеклиста workflow-rules: empty, boundary, concurrency,
  external-failure, permission, malformed-input, deleted-resource; frontend — + browser/UX) с
  ожидаемым поведением (reject/degrade/retry/propagate).
- **Verify-гейт = исполняемый смоук**, не type-check. Если фаза производит инфру/контракт для
  следующих (test-harness, валидатор, API-client, shared-config, миграция) — гейт ОБЯЗАН реально
  исполнить код (один запрос/рендер/CLI-вызов/импорт). Слабый гейт пропускает дефект в следующую фазу.
- **Контракт для следующих фаз** — если фаза производит то, что потребляют downstream-фазы, опиши
  сигнатуру/формат явно и добавь строку «следующий шаг: …» (она уйдёт в журнал).

### Отложенные решения — pre-authorized default + fallback

Что объективно нельзя решить до имплементации — НЕ откладывай в вопрос пользователю. Пиши явный
default + условие fallback, чтобы executor шёл сам:

> Default: использовать `X`. Если при имплементации окажется `<условие>` — fallback на `Y`.

`autonomy=needs-human` ставь ТОЛЬКО на необратимое / прод-риск (DROP, деплой, прод-миграция схемы,
смена публичного API-контракта, удаление данных, SSH на прод). Всё обратимое/дешёвое в откате —
`auto` с default+fallback.

## Размер и группировка фаз

Цель: одна фаза = одна сессия ≈ 30% контекста (max 40%), но не тривиально мелкая.

- **Метрика — число ментальных моделей / файловых поддеревьев**, которые фаза заставляет держать
  одновременно, не LOC. Один домен = одна модель = низкий контекст.
- **Домен-первичен:** фаза не смешивает разные домены. Границы и порядок ведёт доменный граф.
- **Огромный домен → дроби** на подфазы `2a/2b` с собственными маркерами и order.
- **Склейка смежных:** несколько мелких доменов, СВЯЗАННЫХ по зависимости/слою, слей в одну фазу,
  если вместе они в бюджете. Линия — «логически связаны И влезают», не «просто рядом».
- **Не дроби в труху:** фаза, грузящая < ~10% контекста и не имеющая своей доменной причины быть
  отдельной — кандидат на склейку со смежной.
- Рантайм-страховка: executor сам раздробит перетяжелённую фазу — оценка может быть «достаточно хорошей», но всё равно целься в бюджет.

## Handoff

После записи файла:

1. **Самопроверка валидности** (до показа): у каждой фазы маркер в пределах 5 строк под заголовком; `order` строго возрастает; каждый `deps`-id ссылается на существующую фазу и не на `needs-human`/`skipped`; `## Журнал` присутствует. Не сходится — чини до показа.
2. Покажи пользователю итоговую разбивку (фазы + домены + порядок).
3. Выдай точную команду запуска: `/circle-skill docs/superpowers/plans/<файл>.md`.
4. Не запускай circle сам — это user-invoked команда.
