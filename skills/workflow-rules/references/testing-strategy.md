# Testing strategy — выбор слоя, right-amount, скорость

Читай перед проектированием тестов нового модуля/фичи. Цель: максимум пойманных багов на минуту прогона — правильный слой для каждого куска кода, ноль лишних тестов.

## Выбор слоя

| Код                                                                            | Слой                                                     | Почему                                                                             |
| ------------------------------------------------------------------------------ | -------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Доменная логика: parser / transform / state machine / бизнес-правило / pure fn | unit (много) + property-based (секция ниже)              | Много веток, нет I/O — дёшево и точно                                              |
| Стык код↔БД: repository / DAO / ORM-запросы                                    | integration против РЕАЛЬНОЙ БД (Testcontainers)          | Моки и in-memory (H2/SQLite) не ловят SQL-ошибки, constraint/FK, JSONB-квирки      |
| Стык handler↔сервис, HTTP-слой                                                 | integration через api-client/supertest, без браузера     | Ловит контрактные баги на порядок дешевле e2e                                      |
| Критичные user-journeys: auth-флоу, оплата, checkout                           | few e2e (headless browser)                               | Только сквозные пути — e2e-пролиферация = получасовые прогоны                      |
| UI-компонент с логикой                                                         | component-тест в реальном браузере (Vitest Browser Mode) | В jsdom нет layout-движка и ~20% web-API (computed styles, ResizeObserver, canvas) |
| Чистая логика фронта: hooks, stores, utils                                     | unit в jsdom/node                                        | Layout не нужен — бери самый быстрый раннер                                        |

Форма сьюта следует из кода, не из догмы «пирамида vs трофи»: домен-heavy → больше unit, API/glue-heavy → больше integration. Общий тест на слой ниже всегда предпочтительнее ещё одного e2e.

## Repo-слой: реальная БД, не моки

- Testcontainers / docker-compose: образ пиновать на прод-версию (`postgres:16.3`, не `latest`), порт только динамический (`getMappedPort`), один контейнер на сьют (singleton), не пер-тест.
- Изоляция — уникальные схемы/имена вместо cleanup, где возможно. Container-reuse — только локально, в CI всегда свежий.
- Тестов немного: против реальной БД — только repo-слой; остальные слои — с test-double репозитория.

## Property-based для чистой логики — генератор входов вместо перечисления

Для parser / transform / state machine / бизнес-правил / pure fn — PBT по умолчанию, в дополнение к example-based на ключевые ветки: fast-check (TS/JS), hypothesis (Python), proptest (Rust), rapid (Go). Ты формулируешь инвариант — движок перебирает злые входы (unicode, пустоты, границы, отрицательные) и shrink-ает падение до минимального контрпримера; это снимает зависимость покрытия от того, вспомнил ли автор конкретный edge.

- Стандартные инварианты: roundtrip `decode(encode(x)) === x`; идемпотентность `f(f(x)) === f(x)`; инвариант выхода (каждый чанк ≤ N символов — ловит класс «Telegram 4096»); эквивалентность наивной эталонной реализации; «не бросает на произвольном входе».
- 3–5 свойств + горстка example-based на документирование контракта — вместо десятков ручных примеров.
- Дефолтные numRuns (≈100) в inner-loop; больше — только в CI nightly. Найденный контрпример коммить как отдельный regression-example.

## Стоп-лист — что НЕ тестировать

- Генераты (`@generated`, `*.gen.*`, `*_pb2.py`, `*.d.ts`) — тестируй генератор, не выхлоп.
- Тривиальные getter/setter, DTO, маппинги и конфиги без логики — их проверяет запуск приложения, не unit.
- Сторонний код и платформу: браузерный рендер CSS, кодеки, WebSocket-протокол, GC. Тестируй свой код, вызывающий их.
- Пиксели: точный рендер шрифтов, антиалиасинг, canvas/WebGL-попиксельно, воспроизведение видео.
- Implementation details: приватные методы, порядок внутренних вызовов, структуру state. Тестируй наблюдаемое поведение — тесты на реализацию ломаются от любого рефакторинга, не поймав ни одного бага.

Over-testing — не «лишняя надёжность»: это минус скорость сьюта и рефакторинга и ложное чувство покрытия.

## Труднотестируемое — что вместо

| Область                   | НЕ тестируй            | Тестируй вместо                                                                                                                      |
| ------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| WebSocket                 | протокол, транспорт    | свою логику поверх fake-server (`msw/ws`, mock-socket): message-handling, reconnect/backoff, буфер недоставленного, binary payload   |
| Canvas / WebGL            | пиксели, GPU           | модель сцены / команды отрисовки (unit); smoke «canvas не пустой» (sample 2–3 пикселей); pixel-diff с tolerance — последнее средство |
| Видео / аудио             | кадры, декодер         | state machine плеера по событиям (`playing/waiting/error` — эмить их на элементе), обработку src-ошибок                              |
| Анимации / transitions    | тайминги браузера      | что класс/стиль навешан; в e2e анимации отключай (`prefers-reduced-motion`)                                                          |
| SFC `.vue/.svelte/.astro` | презентационный шаблон | логику `<script>` (computed/watch/handlers) unit-ом; компонент с логикой — в браузерном раннере                                      |
| Стили / CSS               | пиксельный рендер      | layout-oracle (ниже); дизайн-токены не тестируй                                                                                      |
| Upload / drag-n-drop      | браузерный механизм    | свой обработчик с fake `File`/`DataTransfer`                                                                                         |

## Layout-oracle — машинная проверка вёрстки без скриншотов

В headless-браузере после рендера обойди видимые элементы:

- клиппинг: `el.scrollWidth > el.clientWidth` → текст вылез за поле;
- наложение: bounding-box сиблингов пересекаются (кроме намеренного absolute/fixed).

Детерминированная геометрия — стабильна кросс-платформенно, без baseline-картинок. Pixel-diff (`maxDiffPixelRatio`) оставляй для случаев, где геометрия слепа (градиенты, canvas-содержимое).

## Скорость прогона

- Inner-loop — селекция: `vitest --changed` / `jest --findRelatedTests` / `pytest --testmon` / `go test ./<pkg>` / `cargo test -p <crate>`.
- Финал — full suite модуля параллельно (`--max-workers` под CPU этой машины), БД-контейнер singleton.
- Каждый новый e2e оправдывай: это критичный journey? Нет → слой ниже.
- Full > 2 мин → зафиксируй стратегию прогона в проектном CLAUDE.md. > 10 мин → обсуди с пользователем (шардирование, e2e в CI-only).
- Флаки-тест чини или удаляй сразу — флак маскирует реальные падения.
- Зрелому проекту: mutation testing (Stryker/mutmut) nightly в CI находит тесты-пустышки; в inner-loop не гонять.

## Anti-patterns

- Coverage-процент как цель → тесты ради процента. Смотри на непокрытые ветки критичной логики, не на цифру.
- `sleep`/жёсткие таймауты → флак и медленно; жди событие/условие.
- Setup моков длиннее assertions → опусти тест на слой ниже (реальная БД/fake-server) или он не нужен.
- Snapshot на большое дерево → ломается от всего, ревью нечитаем. Snapshot — маленький и осмысленный.
